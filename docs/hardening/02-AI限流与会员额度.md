# 批次二：AI 限流、配额与会员门槛

## 问题

三条会调用上游大模型的入口只有 `requireUser()`，没有任何频率或额度约束：

| 入口 | 文件 |
| --- | --- |
| 讲题助教 | `src/app/api/agent/tutor/questions/[questionId]/route.ts` |
| 知识问答 | `src/app/api/agent/knowledge/sessions/[sessionId]/messages/route.ts` |
| 笔记重生成 | `src/app/api/agent/notes/[noteId]/regenerate/route.ts` |

`runtime-limits.ts` 只约束单次运行（4 轮、6 次工具调用、45 秒超时），不约束调用**次数**。`hasActiveMembership` 在整个 `src/server/agent/` 下零引用，付费门槛完全没接入 AI 功能。`src/lib/api/response.ts` 里定义好的 `RATE_LIMITED` 错误码没有任何地方发出。

最严重的是提交练习后的自动错题复盘：`submit/route.ts` 在 `after()` 里调用 `autoAnalyzeSubmittedSessionMistakes`，对本次错题串行跑最多 10 次完整 Agent。这段逻辑在响应返回**之后**执行，客户端无需等待，脚本循环「建专项练习 → 全部答错 → 提交」即可持续放大成上游调用洪峰。上游 API Key 全局共享，后果是账单失控并触发 429，进而拖垮所有用户的助教功能。

另有一个付费绕过：助教工具 `search_related_questions` 检索同类题时不过滤 `isVipOnly`，会把 VIP 题的题干、正确答案与解析交给模型转述给非会员。

登录接口同样没有失败次数限制，可在线暴力破解。

## 方案

### 1. Redis 滑动窗口限流

新增 `src/server/rate-limit/limiter.ts`。判定与计数在同一段 Lua 脚本里完成（`ZREMRANGEBYSCORE` → `ZCARD` → `ZADD`），保证并发下不会超发。

关键设计：**Redis 不可用时拒绝放行**。限流是这些入口唯一的成本防线，失效时放开等于回到问题本身。未配置 `REDIS_URL` 的本地开发环境则直接放行并打印一次警告。

新增 `resetRateLimit`，用于把登录的语义从「N 次尝试」变成「连续失败 N 次」——验证通过即清零，正常用户不会因为偶尔输错被锁。

### 2. 额度策略

`src/server/rate-limit/policies.ts` 集中定义额度，全部可用环境变量覆盖：

| 场景 | 默认值 | 环境变量 |
| --- | --- | --- |
| AI 突发 | 5 次/分钟 | `AGENT_RATE_LIMIT_PER_MINUTE` |
| AI 小时窗 | 60 次/小时 | `AGENT_RATE_LIMIT_PER_HOUR` |
| AI 每日（免费） | 40 次/天 | `AGENT_RATE_LIMIT_DAILY_FREE` |
| AI 每日（会员） | 400 次/天 | `AGENT_RATE_LIMIT_DAILY_MEMBER` |
| 自动错题复盘 | 60 次/天 | `AGENT_RATE_LIMIT_AUTO_REVIEW_DAILY` |
| 登录 | 5 次/分钟、20 次/小时 | `LOGIN_RATE_LIMIT_PER_MINUTE`、`LOGIN_RATE_LIMIT_PER_HOUR` |

三条 AI 入口**共用同一份额度**（scope 为 `agent-chat`）：它们打的是同一个上游 API Key，分开计量无法约束总成本。

### 3. 接入

- `src/server/agent/shared/quota.ts` 提供 `assertAgentChatQuota(user)`，内部查会员状态后套用对应额度，三条路由在解析请求体后、启动流式响应前调用。
- 自动错题复盘改为**每道题单独消耗一次配额**（`tryConsumeAutoReviewQuota`），超额时静默跳过并记录 `throttled` 计数，而不是让请求失败——它跑在 `after()` 里，抛异常没有意义。
- 登录限流放在 `authorize` 内而不是登录 Server Action 内：`/api/auth/callback/credentials` 是公开端点，攻击者会绕过页面直接打它。同时按邮箱与来源 IP 两个维度计量。

### 4. 错误呈现

- `apiError` 支持自定义响应头，`RateLimitedError` 映射为 **429 + `Retry-After`**。
- 新增 `src/features/agent/agent-chat-fetch.ts`，给 `DefaultChatTransport` 的 `fetch` 做包装。默认实现会把整段 JSON 错误体当作提示展示给学员，包装后还原成服务端写好的中文提示。助教与知识问答两处都接入。
- 登录页新增 `RateLimited` 错误态，提示「登录失败次数过多，请稍后再试」。

### 5. 会员可见性

`search_related_questions` 改为接收 `userId`，复用刷题侧同一个 `buildPracticeQuestionWhere({ hasMembership })`，非会员检索不到 VIP 题。`membership.ts` 新增 `hasActiveMembershipForUser(userId)`，供只拿得到 userId 的 Agent 工具使用。

## 验证

单元测试 10 条（`limiter.test.ts` 8 条 + `api-errors.test.ts` 2 条），覆盖额度递减、超限拒绝、主体隔离、scope 隔离、reset 恢复、Redis 异常拒绝放行、429 响应形状。

针对本机真实 Redis 的集成验证（Lua 脚本在单测里是 mock 的，必须实测）：

```
真实 Redis 滑动窗口: ['允许 remaining=2', '允许 remaining=1', '允许 remaining=0', '拒绝 retry=5', '拒绝 retry=5']
并发 10 次 limit=3，实际放行: 3        <- Lua 原子性确认
第二次被拦截: true | reset 后恢复放行: true
```

执行的命令：`npm run typecheck`、`npm run lint`、`npm test`（33 文件 / 116 用例通过）、`npm run build`。

未做完整登录 E2E：本机 3306 端口开放但数据库连接池超时，无法登录取会话。

## 部署注意

生产环境**必须**配置 `REDIS_URL`，否则限流会被禁用（启动时打印警告）。额度默认值偏保守，可按实际用量用上表的环境变量调整。
