# 提交事务批量化

## 问题背景

练习提交事务（`submitPracticeSession`）在处理 20 道题目时会产生 690+ 条 SQL 语句，导致响应时间长达 546ms，成为性能瓶颈。

### 原有实现的问题

```typescript
// 原有模式：逐行操作
for (const answer of answers) {
  await tx.practiceAnswer.update({ where: { id: answer.id }, data: { isCorrect } });
}

for (const tagId of tagIds) {
  const existing = await tx.userTagStats.findUnique({ where: { userId_tagId: { userId, tagId } } });
  if (existing) {
    await tx.userTagStats.update({ where: { id: existing.id }, data: { answeredCount: { increment: 1 } } });
  } else {
    await tx.userTagStats.create({ data: { userId, tagId, answeredCount: 1 } });
  }
}

for (const questionId of wrongQuestionIds) {
  const existing = await tx.wrongQuestion.findUnique({ where: { userId_questionId: { userId, questionId } } });
  if (existing) {
    await tx.wrongQuestion.update({ where: { id: existing.id }, data: { errorCount: { increment: 1 } } });
  } else {
    await tx.wrongQuestion.create({ data: { userId, questionId, errorCount: 1 } });
  }
}
```

**SQL 数量分析（20 题）：**
- PracticeAnswer 更新：20 条
- UserTagStats 查询 + upsert：50 个标签 × (1 查询 + 1 更新) = 100 条
- WrongQuestion 查询 + upsert：假设 8 道错题 × (1 查询 + 1 更新) = 16 条
- PracticeSession 更新：1 条
- 其他杂项（lastPracticedAt、基础训练等）：~553 条
- **总计：690 条 SQL**

## 解决方案

### 核心思路

将逐行操作改为批量 SQL，利用 MySQL 的 `CASE` 表达式和 `IN` 子句：

1. **批量更新**：一条 SQL 更新多行，使用 `CASE WHEN id = ? THEN ? END` 为每行设置不同值
2. **批量增量**：使用 `SET col = col + CASE WHEN id = ? THEN ? ELSE 0 END` 实现分行增量
3. **先创建后更新**：用 `createMany` + `skipDuplicates` 确保行存在，再批量更新，避免并发竞争

### 实现模块

#### `practice-batch-writes.ts`

导出以下函数：

```typescript
// 批量更新 PracticeAnswer.isCorrect
function buildPracticeAnswerUpdate(
  updates: Array<{ id: string; isCorrect: boolean }>
): Prisma.Sql;

// 批量增量更新 UserTagStats（answeredCount/correctCount/wrongCount/accuracy）
function buildTagStatsUpdate(
  userId: string,
  rows: Array<{ tagId: string; answeredDelta: number; correctDelta: number; wrongDelta: number }>
): Prisma.Sql;

// 批量插入/更新 WrongQuestion 错题记录
function buildWrongQuestionUpdate(
  userId: string,
  rows: Array<{ questionId: string; errorDelta: number; lastErrorAt: Date }>
): Prisma.Sql;

// 批量标记错题为已掌握
function buildWrongQuestionResolve(
  userId: string,
  questionIds: string[]
): Prisma.Sql;

// 写冲突与死锁自动重试（指数退避，最多 3 次）
async function runWithWriteConflictRetry<T>(
  fn: () => Promise<T>,
  maxAttempts = 3,
  baseDelayMs = 25
): Promise<T>;

// 检测 MySQL 唯一约束冲突与死锁错误
function isWriteConflictError(error: unknown): boolean;

// 按最大批次大小分块（默认 100）
function chunk<T>(array: T[], size: number): T[][];
```

#### 批量 SQL 示例

**buildTagStatsUpdate** 生成的 SQL：

```sql
UPDATE `UserTagStats`
SET `answeredCount` = `answeredCount` + CASE
      WHEN `tagId` = '公务员-行测' THEN 5
      WHEN `tagId` = '公务员-申论' THEN 3
      ELSE 0
    END,
  `correctCount` = `correctCount` + CASE
      WHEN `tagId` = '公务员-行测' THEN 3
      WHEN `tagId` = '公务员-申论' THEN 2
      ELSE 0
    END,
  `wrongCount` = `wrongCount` + CASE
      WHEN `tagId` = '公务员-行测' THEN 2
      WHEN `tagId` = '公务员-申论' THEN 1
      ELSE 0
    END,
  `accuracy` = CASE
    WHEN `answeredCount` > 0
    THEN ROUND(`correctCount` * 100 / `answeredCount`, 2)
    ELSE NULL
  END,
  `lastPracticedAt` = '2026-07-27 00:00:00',
  `foundationTagId` = CASE
    WHEN `tagId` = '公务员-行测' AND `foundationTagId` IS NULL AND `correctCount` >= 10 THEN '行测基础'
    WHEN `tagId` = '公务员-申论' AND `foundationTagId` IS NULL AND `correctCount` >= 10 THEN '申论基础'
    ELSE `foundationTagId`
  END,
  `updatedAt` = '2026-07-27 00:00:00'
WHERE `userId` = 'user123'
  AND `tagId` IN ('公务员-行测', '公务员-申论')
```

**关键实现细节：**

1. **accuracy 计算**：直接使用 `correctCount * 100 / answeredCount`，而不是 `(correctCount + delta) / (answeredCount + delta)`
   - MySQL 的 `SET` 子句按顺序求值，`accuracy` 表达式执行时 `answeredCount` 和 `correctCount` 已经是增量后的值
   - 如果用 `+ delta` 会导致重复计数（计算出 40% 而不是正确的 50%）

2. **foundationTagId 赋值**：使用 `CASE WHEN ... AND foundationTagId IS NULL ... THEN ... ELSE foundationTagId END`
   - 条件满足时赋新值，否则保持原值
   - 确保只在首次达标时赋值，避免重复触发

### 重构后的 `submitPracticeSession`

```typescript
export async function submitPracticeSession(sessionId: string, userId: string) {
  const submitTransactionOptions = { timeout: 30_000, maxWait: 10_000 };
  
  const submitted = await runWithWriteConflictRetry(() =>
    prisma.$transaction(async (tx) => {
      // 1. 批量更新 PracticeAnswer.isCorrect (1 条 SQL)
      if (answerUpdates.length > 0) {
        await tx.$executeRaw(buildPracticeAnswerUpdate(answerUpdates));
      }

      // 2. 确保 UserTagStats 行存在 (1 条 SQL，skipDuplicates)
      const sortedTagIds = Array.from(allTagIds).sort((a, b) => a.localeCompare(b));
      await tx.userTagStats.createMany({
        data: sortedTagIds.map(tagId => ({ userId, tagId })),
        skipDuplicates: true,
      });

      // 3. 批量增量更新 UserTagStats (1 条 SQL)
      await tx.$executeRaw(buildTagStatsUpdate(userId, tagStatsRows));

      // 4. 确保 WrongQuestion 行存在 (1 条 SQL，skipDuplicates)
      const sortedWrongQuestionIds = Array.from(allWrongQuestionIds).sort((a, b) => a.localeCompare(b));
      await tx.wrongQuestion.createMany({
        data: sortedWrongQuestionIds.map(questionId => ({ userId, questionId })),
        skipDuplicates: true,
      });

      // 5. 批量更新 WrongQuestion (2 条 SQL：新增错题 + 纠正错题)
      if (wrongQuestionUpdates.length > 0) {
        await tx.$executeRaw(buildWrongQuestionUpdate(userId, wrongQuestionUpdates));
      }
      if (resolvedQuestionIds.length > 0) {
        await tx.$executeRaw(buildWrongQuestionResolve(userId, resolvedQuestionIds));
      }

      // 6. 更新 PracticeSession (1 条 SQL)
      return await tx.practiceSession.update({
        where: { id: sessionId },
        data: { submittedAt: new Date(), status: 'COMPLETED' },
      });
    }, submitTransactionOptions)
  );

  return submitted;
}
```

**SQL 数量对比（20 题）：**
- PracticeAnswer 批量更新：1 条
- UserTagStats createMany + 批量更新：2 条
- WrongQuestion createMany + 批量更新：3 条
- PracticeSession 更新：1 条
- 其他操作（基础训练、学习笔记等）：~11 条
- **总计：18 条 SQL**

## 并发安全

### 问题 1：唯一约束冲突

**场景：** 两个并发事务同时提交，都发现 `UserTagStats` 不存在，都尝试创建。

**原有方案（失败）：**
```typescript
const existing = await tx.userTagStats.findUnique({ where: { userId_tagId } });
if (!existing) {
  await tx.userTagStats.create({ data: { userId, tagId } }); // ← 冲突！
}
```

**新方案（成功）：**
```typescript
// 步骤 1：先创建所有行，跳过已存在的
await tx.userTagStats.createMany({
  data: tagIds.map(tagId => ({ userId, tagId })),
  skipDuplicates: true, // ← 关键：MySQL INSERT IGNORE，不会报错
});

// 步骤 2：批量更新所有行（此时行已存在）
await tx.$executeRaw(buildTagStatsUpdate(userId, rows));
```

### 问题 2：死锁

**场景：** 两个并发事务以不同顺序锁定行，产生循环等待。

```
事务 A：锁定 tag1 → 等待 tag2
事务 B：锁定 tag2 → 等待 tag1
→ 死锁！MySQL 回滚其中一个事务（Error 1213）
```

**解决方案：**

1. **确定性锁顺序**：所有批量操作的目标 ID 按字典序排序
   ```typescript
   const sortedTagIds = Array.from(allTagIds).sort((a, b) => a.localeCompare(b));
   const sortedQuestionIds = Array.from(allQuestionIds).sort((a, b) => a.localeCompare(b));
   ```
   - 确保事务 A 和事务 B 都按 `tag1 → tag2` 顺序锁定，不会产生循环等待

2. **自动重试**：即使死锁发生，也能自动恢复
   ```typescript
   await runWithWriteConflictRetry(() =>
     prisma.$transaction(async (tx) => {
       // ... 事务逻辑
     }, { timeout: 30_000, maxWait: 10_000 })
   );
   ```
   - 检测到死锁（1213）或唯一约束冲突（1062）时，指数退避重试
   - 最多重试 3 次，基础延迟 25ms

3. **增加事务超时**：从默认 5s 增加到 30s
   - 批量操作需要更多时间完成
   - 避免因超时导致的事务回滚

## 注意事项

### MySQL 特定行为

1. **SET 子句顺序求值**
   ```sql
   UPDATE table
   SET a = a + 1,
       b = a * 2  -- ← 这里的 a 是 a + 1 后的值，不是原值
   ```
   - 这是 MySQL 的特性，PostgreSQL 不同（PostgreSQL 的 SET 子句同时求值）
   - 因此 `accuracy` 计算直接使用列值，不需要加 delta

2. **skipDuplicates 对应 INSERT IGNORE**
   ```typescript
   await prisma.userTagStats.createMany({
     data: [{ userId, tagId }],
     skipDuplicates: true, // ← MySQL: INSERT IGNORE，PostgreSQL: ON CONFLICT DO NOTHING
   });
   ```
   - MySQL 不会报错，只是跳过重复行
   - 确保后续 UPDATE 能找到行

3. **死锁检测与回滚**
   - MySQL InnoDB 自动检测死锁，回滚其中一个事务
   - 错误码 1213：`Deadlock found when trying to get lock`
   - 必须在应用层重试

### Prisma 限制

1. **不支持 UPSERT 批量操作**
   - `upsert()` 只能单行，无法批量
   - 必须改为"createMany + update"模式

2. **$executeRaw 不返回受影响行数**
   - 无法验证 UPDATE 是否实际更新了行
   - 必须在事务前 createMany 确保行存在

3. **事务超时配置**
   - 默认 5s，批量操作可能不够
   - 必须显式设置 `{ timeout: 30_000, maxWait: 10_000 }`

## 未来优化方向

1. **Redis 缓存热点标签统计**
   - UserTagStats 是高频更新表，可用 Redis 缓存
   - 每 N 次提交批量刷入数据库

2. **异步队列处理非关键路径**
   - 学习笔记生成、错题分析等可异步处理
   - 进一步减少提交事务时间

3. **分片策略**
   - 按 userId 分片，避免热点用户锁竞争
   - 需要数据库架构调整

4. **监控死锁频率**
   - 记录 `isWriteConflictError` 触发次数
   - 如果频繁发生，考虑调整锁策略
